Terminal-first

No separate “AI terminal”. Your existing CLI workflow stays untouched — ckit just wraps around it.

Code intelligence

codegraph + codebase-memory MCP index your repo so the AI answers “where / what / impact” in one call — far fewer tokens than grep. ckit harness wires it up per project.

Context-aware

Whichever project you enter, the AI picks up its context. Memory is shared via AGENTS.md + agents/*. ckit harness builds it all with one command.

Skill injection

37 skills bundled. ckit skill add <github-url> clones into both the global ~/.omp/skills/ and the project's .omp/skills/.

Quick start

Grab the prebuilt binary, then ckit setup installs the AI core (omp + codegraph + MCP servers + skills). Pick your platform.

macOS & Linux

bash 
# 1. Install the prebuilt binary (no git/rust/cargo)
curl -fsSL https://raw.githubusercontent.com/dante241/ckit_agent/main/install.sh | sh

# 2. Install the AI core (omp + codegraph + MCP + skills + gh)
ckit setup
ckit doctor            # verify

Lands in ~/.local/bin/ckit. Linux (CachyOS/Arch) also gets the kitty 3-pane session + optional profiles; on macOS the Arch-only profiles & desktop bits are skipped automatically.

Windows (PowerShell)

powershell 
# 1. Install ckit.exe + patch your user PATH
irm https://raw.githubusercontent.com/dante241/ckit_agent/main/install.ps1 | iex

# 2. Install the AI core (omp + codegraph + MCP + skills)
ckit setup
ckit doctor            # verify

ckit setup needs these on PATH first (all cross-platform): bun (or Node npm) for omp + codegraph, winget for gh, and optional uv for the headroom/serena MCP servers. Arch-only profiles & the kitty session are Linux-only and skipped.

verify the install 
# ckit doctor is the single source of truth — it checks PATH, the binary,
# omp, codegraph, MCP servers, GitHub auth, and project/harness state.
ckit doctor

# …or check the pieces one by one:
ckit --version         # prints the installed ckit version
omp --version          # AI engine present
codegraph --version    # code index present
gh auth status         # GitHub CLI logged in (needed by ckit ship)

A good install shows ckit doctor with green checks and no “stale state”. If a line is red, re-run ckit setup (idempotent) or install the tool it names, then run ckit doctor again.

Build from source (any OS): git clone https://github.com/dante241/ckit_agent then cargo build --release — or bash scripts/bootstrap.sh on Unix.

How to use ckit

Two phases: a one-time setup for the machine and each project, then day-to-day you just open omp and code.

One-time setup

ckit setupMachine: install omp, codegraph, MCP servers, skills, GitHub CLI.
ckit doctorVerify PATH, GitHub auth, omp, MCP tools, and profiles.
cd <project>Move into the repo you want the AI to understand.
ckit harnessPer-project, run once: skills, codegraph index, AGENTS.md, agents/* memory, hooks, rules. Re-run only after big changes.

Daily: open omp and code

Day-to-day you live inside omp: open the session, then chat, edit, and drive the AI with / commands. No harness verbs needed.

ckit .Open/resume the session → drops you into omp with project context loaded. (or run omp directly)
/auto <task>in omp — one-pass bug fix or small change.
/plan <task>in omp — plan, then execute a larger change.
/feature new|plan|go|shipin omp — multi-phase feature with acceptance criteria.

Optional shell shortcuts (no need to enter omp): ckit ai "…", ckit find <kw>, ckit run dev|test, ckit note "…", ckit ship "…".

a day with ckit 
# open the project session — you're now inside omp
cd ~/code/my-app
ckit .

# then just talk to the AI inside omp:
/auto fix the flaky login test
/plan add rate limiting to the API
/feature new customer-portal      # long, multi-phase work with acceptance criteria

Use /auto for small bugs or one-pass work; use /feature when the work spans many files, phases, or days and needs acceptance criteria tracked in agents/planning/<slug>/.

Configure & verify

After ckit setup, a few files control omp — and one command confirms the AI tooling is live.

Config files

~/.omp/agent/config.ymlomp behaviour: memory backend (Mnemopi, per-project), auto-compaction threshold, model roles, tool approval.
~/.omp/agent/models.ymlModel catalog + the gateway API key and endpoint URL. Set the values you were given with ckit harness gateway key <KEY> and ckit harness gateway url <URL>, then ckit harness gateway verify — don't hand-edit the substituted values.
~/.config/ckit/models.tomlWhich model per role/task class (plan · review · debug · code · trivial) for ckit ai.
~/.omp/agent/mcp.jsonThe registered MCP servers — managed by ckit harness.

Verify MCP inside omp

Open a session (ckit .), then run /mcp list. On macOS/Linux all four connect; on Windows codebase-memory-mcp may be skipped (no installer yet):

/mcp list 
Configured MCP Servers
User level (~/.omp/agent/mcp.json):
  codebase-memory-mcp  ● connected [stdio]
  codegraph            ● connected [stdio]
  headroom             ● connected [stdio]
  serena               ● connected [stdio]

A server missing or not connected? Re-run ckit harness to re-register, then ckit doctor. On Windows, codebase-memory-mcp may be skipped (no installer yet).

set the gateway key + endpoint · migrate old memory 
# point omp at the model gateway you were given → writes ~/.omp/agent/models.yml
ckit harness gateway key <YOUR_API_KEY>
ckit harness gateway url http://<host>:<port>/v1
ckit harness gateway verify        # 200 = healthy

# bring an existing Claude Code project into omp: imports the session, and
# Mnemopi (omp's per-project long-term memory) recalls/retains as you work
cd <your-project>
omp --from-claude        # or: omp --from-codex

Memory lives in omp's Mnemopi store (set in config.yml, scoped per project). Inside a session the AI uses recall/reflect to read it and retain to save durable facts — no manual file editing needed.

Command reference

Daily work happens inside omp (open with ckit ., then drive it with / commands). The verbs below are optional shell shortcuts and lifecycle/tools — you don't need them to code. Every verb has -h / --help; run ckit help for the cheatsheet.

Optional shell shortcuts

ckit .Open/attach a session (kitty 3-pane + omp --continue inside abduco)
ckit ai [prompt]Empty → resume; with a prompt → one-shot omp -p
ckit find <kw>rg/fd + fzf, opens the editor at file:line
ckit note "msg"Appends to agents/NOTES.md
ckit run dev|build|test|fmt|lintRecipe-based project runner
ckit ship "msg"git add -A && commit && push && gh pr create
ckit feature new|switch <slug>Large multi-phase scopes (GSD): planning tree + AC gates + ACTIVE switch; then /feature plan|go|ship in omp

Lifecycle & tools

Skill injection

A skill is an instruction module for the AI. ckit bundles 37 skills (codegraph · karpathy · ponytail · assp · impeccable · taste · 8sync-cli · image-routing · feature (large-scope GSD) + 18 research skills · …); ckit skill add is collection-aware and pulls whole sets from GitHub.

bash 
# Clone from a URL: installs into BOTH ~/.omp/skills/ (global, read by omp) and .omp/skills/ (project)
# Also rewrites the <!-- ckit:skills:* --> block in AGENTS.md
ckit skill add https://github.com/colbymchenry/codegraph

# Other spec forms
ckit skill add gh:owner/repo
ckit skill add path:/abs/local/dir
ckit skill add builtin:karpathy

# Idempotent: re-running = git pull --ff-only
ckit skill add https://github.com/colbymchenry/codegraph   # → "updated"

# Build / refresh the whole harness (replaces the old `skill sync`)
ckit harness init
ckit harness up --timer 30m

Update

Two ways:

Auto (recommended)

ckit up

Self-updates the binary (GitHub release) + omp update. Never touches pacman -Syu.

Manual (build from source)

cd ckit_agent && git pull
cargo build --release
install -m755 target/release/ckit \
  ~/.local/bin/ckit

Release & docs update

Cutting a version keeps code, changelog, and this site in lockstep — no manual HTML edit:

# 1. bump the workspace version:  Cargo.toml → version = "X.Y.Z"
# 2. promote the changelog: rename "## [Unreleased]" → "## [X.Y.Z] - YYYY-MM-DD"
#    and add a fresh empty [Unreleased] above it
git commit -am "release: vX.Y.Z"
git tag vX.Y.Z && git push && git push --tags

The vX.Y.Z tag fires release.yml (every-OS binaries + GitHub Release). The push to main fires pages.yml, which copies CHANGELOG.md into docs/ and redeploys — the Changelog section above updates itself.
