# Delta re-review of an already-reviewed GitLab MR

When `/review-pr <N>` hits an MR with a prior "Reviewed by Dante" comment and a NEWER head SHA, do NOT re-derive findings for the whole MR. Review = (a) verify every old blocking finding on the new head, (b) review only the delta's new code.

## Procedure

1. **Detect re-review**: `glab api projects/<repo>/merge_requests/<N>/notes?sort=asc` → find latest Dante review comment; compare its reviewed SHA (from commit list timestamps) vs current `sha` from `glab api .../merge_requests/<N>`.
2. **Extract prior findings**: save the full latest review comment (`.../notes/<id> | jq -r .body`) as `$PREVIOUS_ISSUES`. Note findings already RETRACTED in prior rounds (e.g. proven-invalid by probe) — never re-flag those.
3. **Delta**: `git fetch origin refs/merge-requests/<N>/head:mr/<N>`; work with the head SHA, not `mr/<N>` (a tag or another ref of that name makes it ambiguous). `git merge-base --is-ancestor <oldHead> <newHead>` true → `git diff <oldHead>..<newHead>` → stat + full diff to /tmp. False (author rebased) → that diff would include every master commit merged in between: use `git range-diff <oldBase>..<oldHead> <newBase>..<newHead>` for the author's own changes and say so in the comment.
4. **Head snapshot without touching the working tree**: `git worktree add /tmp/mr<N> <newHeadSha> --detach` (remove stale non-worktree dir first if `already exists`). All verification reads THIS path. Clean up only AFTER every verification step is done: `git worktree remove /tmp/mr<N> --force`.
5. **Verification mode — pick by delta size and DECLARE the choice**:
   - **Delta > ~1500 lines or >30 files** → parallel agents (one `tasks[]` batch, code-reviewer type): split by prior-finding severity + new code — e.g. VerifyHigh / VerifyPerf+partials / ReviewNewCode / VerifyMedium+rest. Pass every agent the coding rules matching the delta's files (`$RULES_CONTEXT`, review-pr Step 2). Contract per finding: `verdict RESOLVED|PARTIAL|UNRESOLVED|NEW` + evidence `file:line` from the worktree (never from commit messages) + confidence ≥80.
   - **Small delta (≤ ~1500 lines)** → direct verification by the orchestrator is acceptable AND usually better (agents duplicate the mandatory self-validation of step 6), but you MUST (i) read 100% of the delta, (ii) verify every referenced symbol/signature/format in the worktree (not the diff alone), (iii) keep the same verdict+evidence+confidence contract, and (iv) explicitly state in your summary that you chose direct verification over the agent batch and why. Silent deviation is the failure mode — an advisor will flag it.
6. **Validate NEW blockers yourself before blocking merge** — agents over-score severity. Two proven downgrades: (a) "migration throw blocks the cron/migration chain" → check the runner: `CPMigration_Migrator_Model::runMirations()` (`modules/CPMigration/models/Migrator.php` ~:118) catches only `Exception`, records success=0 and continues (retries only success=0 rows) — downgrade ONLY when `up()` throws an `Exception`; an `Error`/`TypeError` escapes the catch and DOES stop the chain (keep the blocker); (b) "ACL fail-open leaks data" → compare vs what an UNFILTERED request already returns; if no new access is granted and the pattern mirrors an already-passed view, it's MEDIUM. Also: `hasGlobalReadPermission()` as a skip-ACL fast path mirrors core vtiger ListView behavior — not a finding. Downgrades must cite runtime evidence, not taste (skill rule: no subjective downgrade — evidence-based rescoring in the validation step is allowed).
7. **Comment format**: reuse the prior comment's structure + a "So sánh với review trước" section (✅ fixed / 🟡 partial / 🆕 new, with strikethrough per fixed finding). Keep the requirement-checklist verdict from before if ticket description is still empty (re-check PMS — it may have been filled since).
8. **Residual blockers** (PERF partials, a CRITICAL the user accepts): still block auto-merge → `ask` (post+merge / post-only / stop). If user approves merge: write the override into the comment (finding stays listed, marked "author/user cho phép merge") → post comment → `glab mr update --unlabel "Cần Fix"` then `--label "Dev done"` → `glab mr merge <N> --squash --squash-message "MR: <original title>" --remove-source-branch --yes` → `pms_ticket_update(id=<record_id>, data={ticketstatus:"Testing", helpdesk_released_version:"unreleased", helpdesk_project_type:"rnd", rating_note:"<markdown, real \n, no HTML tags>"})` (ticket already in Testing → the update still succeeds; check `valid_next_statuses` only when moving from another status).

## Traps
- `/tmp/mr<N>` may exist as a stale plain dir from an earlier session → `worktree add` fails with `already exists`; rm -rf then re-add.
- Run `glab mr …` from the repo root (or pass `-R <group>/<project>`): from `/tmp/...` glab cannot resolve the project and answers 404. Before retrying a failed post, list the MR notes so the review is not posted twice.
- PMS ticket search: `ticket_no` exact (`operator: "e"`) with the hash (`#NNNNN`, as stored); `c` with a bare number also matches `#1NNNNN`. `pms_ticket_detail` needs the numeric record_id, not the ticket_no.
- Fix commits can introduce NEW findings inside the fixes themselves (e.g. an ACL guard that fails open, a migration that throws on dirty data) — always review the delta's new code as new code, not just as finding-verification.
- Verify fix-referenced symbols in the WORKTREE, not the diff: a fix calling `assignPageMerged`/`hasGlobalReadPermission` is only RESOLVED once the method's existence, visibility, and signature are confirmed on the new head; same for data formats (e.g. a restore path must match the exact keys/format the save path serializes: `article_id`/`date Y-m-d`/`time H:i`).
- Don't remove the worktree until the LAST verification read is done — re-creating it from the head SHA is cheap but interrupts flow.
